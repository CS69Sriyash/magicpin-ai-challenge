## 1. PROJECT OVERVIEW

### 1.1 Project Purpose & Vision

**Vera** is a WhatsApp-based AI assistant designed to engage and assist merchant partners on the magicpin platform. The bot acts as an autonomous marketing and operational assistant for merchants across diverse business categories (dentists, salons, restaurants, gyms, pharmacies), helping them:

- Improve Google Business Profile (GBP) visibility
- Execute data-driven marketing campaigns
- Receive category-specific business intelligence and trend analysis
- Book customer appointments or close simple transactions
- Respond to customer inquiries on the merchant's behalf

### 1.2 Challenge Constraints & Architecture Decisions

**Key Constraints**:
- **30-second execution timeout** per API call (the judge harness deadline)
- **Stateless API design** with in-memory context store (required by the judge)
- **Conversational state tracking** across multiple interactions with merchants
- **WhatsApp auto-responder detection** to avoid engagement loops
- **Hallucination prevention** through anchor-fact extraction from structured data

**Core Architectural Decisions**:

| Tradeoff | Choice | Rationale |
|----------|--------|-----------|
| **In-Memory vs Persistent DB** | In-memory dictionary | High speed under 30s budget; state lost on container restart acceptable for challenge scope |
| **Heuristics vs Pure LLM** | Deterministic Python + LLM fallback | Guarantees safety on critical exits (stop, spam, auto-reply); avoids LLM hallucinations |
| **Single vs Multi-Model** | Groq `llama-3.3-70b-versatile` + Gemini fallback | Maintains low latency; 12K TPM on free tier vs Qwen's 8K |
| **Rate Limiting** | Adaptive token-bucket with real-time adjustment | Prevents TPM/RPM throttling; tracks actual tokens vs worst-case estimates |

## 3. CORE FUNCTIONS & MODULES BREAKDOWN

### 3.1 LLM Provider Interface

```python
class LLMProvider(ABC):
    """Abstract interface for all LLM backends."""
    
    name: str  # "ollama", "groq", "gemini"
    
    @abstractmethod
    async def compose(self, prompt: str, system: str) -> str:
        """Compose a message; raise LLMError on failure."""
        pass
```

**Implementations**:

| Provider | Endpoint | Rate Limit | Timeout | Default Model | Use Case |
|----------|----------|-----------|---------|---------------|----------|
| **OllamaProvider** | `http://localhost:11434/api/generate` | None | 20s | `qwen2:7b` | Local dev/iteration |
| **GroqProvider** | `api.groq.com/openai/v1/chat/completions` | 12,000 TPM (free) | 20s | `llama-3.3-70b-versatile` | Production (primary) |
| **GeminiProvider** | `generativelanguage.googleapis.com/v1beta` | 250K TPM (free) | 20s | `gemini-2.5-flash` | Production (fallback) |

**Rate Limiting Strategy** (`_TokenRateLimiter`):
- Tracks rolling 60-second window of token usage
- Adaptive: reserves worst-case tokens before call, then adjusts with actual provider usage
- Prevents self-throttling when real usage is lower than estimate
- Shared across `/v1/tick` and `/v1/reply` calls to serialize against quota

### 3.2 Auto-Reply Detection System

**Problem**: WhatsApp Business auto-responders ("Thank you for contacting...") pollute 40–70% of merchant replies; production Vera detects but burns 2–3 turns.

**Solution**: Cross-conversation fingerprinting + boilerplate pattern matching

```python
def _check_cross_conversation_auto_reply(merchant_id: str, message: str) -> bool:
    """
    Merchant-scoped (not conversation-scoped) duplicate check.
    Returns True if this inbound message:
    1. Exactly matches a prior fingerprint (with digits normalized), OR
    2. Contains boilerplate pattern AND last message was also boilerplate
    
    Always logs the current message before returning.
    """
```

**Fingerprinting**:
- Normalize: lowercase → collapse whitespace → replace digits with `#`
- Reason: Auto-responders often vary only in ticket number or timestamp

**Boilerplate Patterns**:
```regex
out of office|auto-?reply|automated (message|response|reply)|
respond(ing)? shortly|thank you for (contacting|reaching out)|
currently (unavailable|away|closed)|will respond as soon as possible
```

**Store**: `MERCHANT_INBOUND_LOG[merchant_id]` — deque of 8 recent `{fp, boilerplate, ts}` tuples; TTL 6 hours

### 3.3 Anchor-Fact Extraction (Hallucination Prevention)

**Problem**: LLMs fabricate or misquote source citations / numbers

**Solution**: Pre-extract structured facts into prompt; require LLM to use them verbatim

**Implementation**:

```python
def _resolve_digest_anchor(category: dict, trigger: dict) -> dict | None:
    """
    For triggers referencing category.digest[] items by ID (e.g., research_digest),
    resolve the item object. Returns None if ID not found.
    """


def _format_anchor_block(category: dict, trigger: dict) -> str:
    """
    Format instruction block for prompt:
    - If digest_item_id found: output ANCHOR FACT with title/source/numbers/credits
    - Else: list full trigger.payload as the fact source

    Instruction: quote source VERBATIM, use exact numbers, don't paraphrase.
    """
```

**Prompt Example**:
```

  title: JIDA Oct 2026 — Fluoride Varnish at 3-Month Recall
  source (quote verbatim): JIDA October 2026 p.14
  summary: 3-month recall protocol reduces caries recurrence 38% better than 6-month
  trial_n: 2,100
  ...
```

### 3.4 EngagementComposer — Main Orchestrator

**Purpose**: Format 4 contexts into a structured prompt, call LLM, validate + parse JSON response

#### **3.4.1 Proactive Composition**

```python
async def compose_proactive(
    category: dict, merchant: dict, trigger: dict, customer: dict | None

    """
    Given merchant + trigger context, compose a proactive message.
    Returns: {
        "body": "<message>",
        "cta": "<label>",
        "rationale": "<why>",

    """
```

**Prompt Structure**:

```python
system_prompt = (

    "3. MERCHANT FIT — use real name/numbers, don't fabricate\n"
    "4. TRIGGER RELEVANCE — reference anchor fact directly\n"
    "5. ENGAGEMENT — one lever (loss aversion, social proof, curiosity, etc.)\n"
    "\nCTA RULES: end with ONE binary choice or one specific question.\n"
    "\n" + FEW_SHOT_BLOCK + "\n"
    "OUTPUT: single JSON object {body, cta, rationale, send_as}"
)

user_prompt = (
    "CATEGORY:\n"
    + json.dumps(category, indent=2)
    + "\n\nMERCHANT:\n"
    + json.dumps(merchant, indent=2)
    + "\n\nANCHOR FACT:\n"
    + _format_anchor_block(category, trigger)
    + "\n\nTRIGGER:\n"
    + json.dumps(trigger, indent=2)
    + ("\n\nCUSTOMER:\n" + json.dumps(customer, indent=2) if customer else "")

```

**Response Validation**:
- Extract JSON (strip markdown fences if needed)
- Validate keys: `body` (non-empty), `cta`, `rationale`, `send_as`
- Check CTA rules: if slot-booking exception, allow up to 2 slots; else exactly 1 CTA

#### **3.4.2 Reactive Composition (Reply)**

```python
async def compose_reply(
    category: dict,
    merchant: dict,
    inbound_message: str,
    conversation_history: list[dict],
) -> dict:
    """
    Given inbound message, decide action: "send", "wait", or "end".
    Returns: {
        "action": "send"|"wait"|"end",
        "body": "..." (if action="send"),
        "cta": "..." (if action="send"),
        "rationale": "..."
        "wait_seconds": int (if action="wait")
    }
    """
```

**System Prompt Includes Strict Rules**:
- **INTENT TRANSITION (Rule 1)**: If merchant agrees ("yes", "let's do it"), action MUST be "send" with confirmation. MUST NOT ask more questions.
- **HOSTILE / STOP (Rule 2)**: If annoyed or says "stop", action MUST be "end". Do not argue or re-pitch.
- **OFF-TOPIC (Rule 3)**: If merchant goes off-topic, politely redirect without dismissal.

### 3.5 Conversation & Suppression Tracking

#### **In-Memory Stores**

| Store | Key | Value | Purpose |
|-------|-----|-------|---------|
| `CONTEXT_STORE` | `(scope, context_id)` | `{version, payload}` | All 4 context types; versioned for idempotency |
| `CONVERSATIONS` | `conversation_id` | `[{turn, from_role, message, ts}, ...]` | Turn-by-turn history |
| `CONVERSATION_META` | `conversation_id` | `{merchant_id, customer_id, category_slug, trigger_id, sent_bodies}` | Metadata; `sent_bodies` = set of prior message bodies |
| `MERCHANT_INBOUND_LOG` | `merchant_id` | `deque[{fp, boilerplate, ts}]` | Cross-conversation auto-reply fingerprints |
| `SENT_SUPPRESSION_KEYS` | `suppression_key` | `True` | Once a trigger fires, mark its suppression_key to avoid re-sends |

#### **Suppression Logic**

When `/v1/tick` is called with `available_triggers`:

```python
for trigger in available_triggers:
    suppression_key = trigger.get("suppression_key")
    
    # Skip if already sent (trigger can only fire once per challenge run)
    if suppression_key in SENT_SUPPRESSION_KEYS:
        continue
    
    # Compose message
    action = await composer.compose_proactive(...)
    
    # Mark as sent to prevent re-delivery
    if action and not error:
        SENT_SUPPRESSION_KEYS.add(suppression_key)
```

### 4.2 Context Resolution Pipeline

**When composing a message**, resolve context in this order:

```python
def compose_proactive(trigger_id):
    trigger = _get_context("trigger", trigger_id)
    merchant_id = trigger["merchant_id"]
    merchant = _get_context("merchant", merchant_id)
    category_slug = merchant["category_slug"]
    category = _get_context("category", category_slug)
    
    customer_id = trigger.get("customer_id")
    customer = _get_context("customer", customer_id) if customer_id else None
    
    prompt = format_prompt(category, merchant, trigger, customer)
    response = await llm_provider.compose(prompt, system)
    return parse_json(response)
```

**Fallback Strategy**:
- Missing merchant → skip this trigger
- Missing category → skip this trigger
- Missing customer (optional) → compose without customer context
- Missing any required field → log warning + skip gracefully

#### **/v1/tick Deadline Loop**

```python
async def tick(triggers):
    deadline = time.monotonic() + 29.0  # Leave 1s buffer before 30s limit
    actions = []
    
    for trigger_id in triggers:
        if time.monotonic() > deadline:
            logger.info("tick: hit deadline, returning partial results")
            break  # Return what we have; judge will retry rest on next tick
        
        try:
            action = await composer.compose_proactive(trigger_id)
            actions.append(action)
        except asyncio.TimeoutError:
            logger.warning("compose timed out for trigger %s", trigger_id)
            continue
        except ComposerError as exc:
            logger.warning("compose error: %s", exc)
            continue
    
    return {"actions": actions}
```

### 4.4 Conversation State Machine

```
[Start]
  │
  ├─► merchant receives bot message via /v1/reply inbound
  │
  └─► check auto-reply fingerprint
      ├─ YES: end conversation (auto-reply loop detected)
      └─ NO: proceed
          │
          └─► load CONVERSATION_META[conversation_id]
              ├─ track "sent_bodies" = {prior message bodies}
              │   (avoid exact repeats in same conversation)
              └─► call compose_reply(inbound_msg)
                  ├─ LLM reads conversation_history
                  ├─ LLM applies strict rules (intent transition, hostile/stop)
                  └─ LLM returns action (send | wait | end)
                      │
                      ├─ "send" ──► add message to history + return
                      ├─ "wait"  ──► add to history but don't return (pause conversation)
                      └─ "end"   ──► close conversation, stop responding
```

### 4.6 Data Persistence & Serialization

#### **What's Stored**:
- All 4 context types (category/merchant/customer/trigger) → `CONTEXT_STORE`
- Conversation turn history → `CONVERSATIONS[conversation_id]`
- Suppression keys → `SENT_SUPPRESSION_KEYS` (one-way: never fires twice)
- Auto-reply fingerprints → `MERCHANT_INBOUND_LOG[merchant_id]` (6-hour TTL)

#### **What's NOT Stored** (Intentional):
- Merchant's real-time Google Business Profile state (provided via context push)
- Customer's actual booking calendar (provided via customer context)
- Real WhatsApp message delivery receipts (out of scope for challenge)

#### **Serialization Format**:
- Input: JSON (Pydantic validates via CategoryContext, etc.)
- Output (LLM response): JSON (extracted + validated)
- Submission results: JSONL (one JSON object per line for streaming)

## 6. ERROR HANDLING & RESILIENCE

### 6.1 LLM Failures

| Failure Mode | Handler | Fallback |
|---|---|---|
| **Timeout** | `asyncio.TimeoutError` | Skip trigger (retry on next tick) |
| **Rate Limit (429)** | Caught by `_TokenRateLimiter.acquire()` | Sleep and retry (built into acquire loop) |
| **API Error (5xx)** | `httpx.HTTPError` → `LLMError` | Log + skip trigger |
| **Malformed Response** | `_extract_json()` fails | Log + skip trigger |
| **Invalid JSON Schema** | Pydantic validation fails | Log + skip trigger |

### 6.2 Context Resolution Failures

| Failure Mode | Handler | Fallback |
|---|---|---|
| **Missing merchant** | `_get_context()` returns None | Skip this trigger entirely |
| **Missing category** | `_get_context()` returns None | Skip this trigger entirely |
| **Missing customer (optional)** | Compose without customer context | Proceed |
| **Stale version push** | `CONTEXT_STORE` version check | Reject with HTTP 409 |

### 6.3 Conversation State Corruption

**Prevention**:
- Sent message bodies tracked in `CONVERSATION_META[...]["sent_bodies"]` set
- Duplicate detection: if LLM produces exact repeat of prior body, mark as error
- Per-merchant auto-reply log with 6-hour TTL and max 8 entries

### 7.1 Time Budget

| Operation | Typical Duration | Budget |
|---|---|---|
| Parse request + load contexts | 10–50 ms | 500 ms |
| LLM compose (Groq) | 500–2000 ms | 15 s |

## 10. KEY DESIGN DECISIONS & TRADEOFFS

### 10.1 Why In-Memory Storage?

**Tradeoff**: In-memory vs persistent DB (Redis, PostgreSQL, etc.)

| Dimension | In-Memory | Persistent DB |
|---|---|---|
| Speed | Sub-millisecond access | 10–100ms network latency |
| Durability | Lost on restart | Survives restarts |
| Complexity | Simple dict | Connection pools, migrations, backups |
| Challenge Fit | ✓ Works with judge | ✓ Also works; overkill |

**Decision**: In-memory. Challenge runs one test at a time; state loss on restart not a problem. Speed is more valuable than durability.

### 10.2 Why Adaptive Rate Limiting?

**Tradeoff**: Static sleep vs adaptive token-bucket

| Approach | Benefit | Cost |
|---|---|---|
| Static sleep (e.g., 2s between requests) | Simple | Wastes time on small requests |
| Adaptive token-bucket | Respects real quota without over-sleeping | Complex; requires real-time adjustments |

**Decision**: Adaptive. Groq's 12K TPM free tier is tight; wasting tokens on excess delays risks hitting quota mid-run.

### 10.3 Why Deterministic Auto-Reply Detection?

**Tradeoff**: Pure heuristics vs LLM classification

| Approach | Benefit | Cost |
|---|---|---|
| Regex + fingerprinting | Fast, zero latency | Misses novel patterns |
| LLM classification | Catches anything LLM can understand | Adds latency + token cost |

**Decision**: Heuristics. Production Vera processes 34K+ messages/day; false negatives (missed auto-replies) are worse than false positives (wrongly ending real conversations).

### 10.4 Why Category-Hardcoded Voice Directives?

**Tradeoff**: Hardcoded tone vs pure context-driven

| Approach | Benefit | Cost |
|---|---|---|
| Hardcoded directives | Consistent tone per category across runs | Less flexible; requires code changes to adjust |
| Pure context (voice field) | Fully data-driven | Can be vague or contradictory if context is malformed |

**Decision**: Both. Hardcoded directives set a clear register (e.g., "clinical" for dentists); live context data supplies vocabulary (taboos, allowed terms). Combines consistency with flexibility.

### 10.5 Why Groq + Gemini (Not OpenAI)?

| Provider | TPM (Free) | Cost | Latency | Reasoning |
|---|---|---|---|---|
| OpenAI | ~150K | $0.50/1M tokens | 500–1000ms | Expensive; slow for challenge |
| Groq | 12,000 | $0 (free) | 100–300ms | Fast, cheap; primary choice |
| Gemini | 250,000 | $0 (free) | 500–2000ms | Fallback; much higher TPM |

**Decision**: Groq primary, Gemini fallback. Groq's speed + free TPM makes it ideal for <30s deadline. Gemini's higher TPM budget acts as insurance if Groq hits rate limits.
